# Android 架构渐进式拆分设计

日期：2026-09-09  
状态：设计已确认，待最终审阅

## 1. 背景

当前应用已经形成 `app / core / feature / platform` 的包级分层，并使用 Kotlin、Jetpack Compose、Room、DataStore、WorkManager 和 Hilt。平台解析、下载、作者库、本地内容、预览和诊断均已有独立概念，核心功能不再是脚本式实现。

随着功能持续增加，若干文件承担了过多职责：

- `HomeScreen.kt` 约 2000 行；
- `TasksScreen.kt`、`MainViewModel.kt` 各约 1500 行；
- `CreatorScreens.kt` 约 1400 行；
- `DownloadExecutor.kt` 约 1100 行。

主要问题不是功能不可用，而是状态和行为边界逐渐模糊。Room、WorkManager、StateFlow 和 Compose 同时参与任务展示；`MainViewModel` 同时协调解析、登录、任务、预览、文件、设置和更新；大型 Compose 文件也混合了页面、卡片、对话框和平台环境。这会提高新增平台和修复状态同步问题的成本。

## 2. 目标

本轮重构的目标是：

- 在不改变任何用户功能的前提下缩小类和文件的职责范围；
- 保持现有包名、应用身份、签名、持久化数据和升级兼容性；
- 明确持久化状态、运行时状态和界面状态的所有权；
- 降低新增平台、修改下载策略和维护页面时的联动范围；
- 保持每个阶段都可独立测试、提交和回滚；
- 暂时保持单一 Gradle `app` 模块，先通过包和接口稳定边界。

本轮不追求机械地消除所有大文件，也不为行数而拆分。拆分后的单元必须具有清晰职责和稳定输入输出。

## 3. 非目标与兼容性硬约束

本轮明确不做以下事情：

- 不改变 `applicationId`、版本更新身份或签名证书；
- 不修改 Room 表结构和数据库版本；
- 不修改现有任务 ID、作者键、作品键或批次 ID 的生成方式；
- 不修改 WorkManager 唯一任务名称、标签和恢复语义；
- 不修改下载目录、文件命名、已有 URI 或存储授权方式；
- 不替换 Compose、Room、WorkManager、Hilt 或现有网络栈；
- 不重新设计 UI，不调整文案、交互和导航结果；
- 不在本轮拆分为多个 Gradle Library 模块；
- 不顺带重写平台接口、下载算法或风控策略。

如果重构过程中发现必须改变用户行为或持久化格式才能继续，该变更从本轮剥离，单独设计和开发。

## 4. 方案选择

采用保留现有 API 的渐进式拆分方案。

`MainViewModel` 和现有页面入口在过渡期间作为兼容门面，调用逐步迁移到职责单一的状态持有者或协调器。每个阶段先建立等价测试，再移动实现，最后清理旧代码。禁止一次性重写整个状态树或导航。

没有采用以下方案：

- 一次性切换为多个 Feature ViewModel：会同时改变导航、状态订阅和页面生命周期，回归面过大；
- 立即多模块化：当前职责边界尚未完全稳定，过早增加 Gradle、Hilt 和可见性约束会放大迁移成本。

## 5. 目标依赖方向

目标调用方向如下：

```text
Compose 页面
    ↓
页面状态持有者 / 兼容 ViewModel 门面
    ↓
用例协调器
    ↓
Repository / 下载运行时 / 平台接口
    ↓
Room、DataStore、WorkManager、HTTP、Android 存储
```

约束：

- `core` 不依赖 `feature` 或具体平台；
- 平台实现依赖公共平台契约和 `core`，公共契约不反向依赖具体实现；
- Compose 组件不直接操作 DAO、WorkManager 或底层 HTTP；
- 文件操作、下载执行和登录检测通过明确接口暴露结果；
- 页面状态只能由其所有者修改，其他组件通过事件或方法请求变更。

## 6. 状态所有权

### 6.1 持久化真相

Room 是以下数据的唯一持久化真相来源：

- 下载任务及状态；
- 输出文件与文件状态；
- 作者资料、公开作品、本地作品归档；
- 批处理记录；
- 知乎问题归档。

DataStore 是以下设置的唯一持久化真相来源：

- 默认下载模式；
- 编码偏好；
- 保存位置；
- 更新设置；
- 平台风控冷却配置和冷却截止时间。

### 6.2 运行时状态

以下状态只存在于运行时组件，不写入任务业务字段：

- 实时下载速度和临时传输采样；
- 动态并发数、CPU 和温度采样；
- 播放位置、播放/暂停、全屏和控制层可见性；
- 当前解析会话中的中间响应和登录环境快照。

需要跨进程恢复的最小状态继续由 WorkManager 输入数据、Room 任务记录或现有任务规格承担。

### 6.3 界面投影

任务页和本地下载页使用同一底层任务记录生成不同投影：

- 任务页只投影仍需处理的活动状态；
- 本地下载页投影存在可用文件或归档记录的内容；
- Compose 不创建第二套永久任务状态。

## 7. 分阶段实施

### 7.1 阶段一：Compose 文件机械拆分

先移动纯 UI 组件，不改变参数、状态来源或事件回调。

首页拆分为：

- 首页页面骨架；
- 输入与解析操作区；
- 平台登录状态区；
- 解析结果与质量选择；
- 登录 WebView 环境；
- 解析错误和加载状态。

任务与本地内容拆分为：

- 任务列表和筛选；
- 独立任务卡片；
- 作者批次卡片与子任务明细；
- 批量操作对话框；
- 图片、视频、音频预览；
- 分享和文件操作入口。

作者页面拆分为：

- 作者列表；
- 作者资料头部；
- 公开作品列表；
- 本地作品列表；
- 排序、筛选和批量操作组件。

组件只接收所需的最小状态和回调，禁止把整个 ViewModel 继续向下传递到所有叶子组件。迁移期间入口函数签名保持兼容。

### 7.2 阶段二：拆解 `MainViewModel`

`MainViewModel` 暂时保留为 `AppContent` 的兼容门面，并逐步委托给以下组件：

- `ParseSessionController`：输入、链接识别、解析会话、质量与模式选择；
- `PlatformCredentialCoordinator`：平台登录状态、WebView 生命周期和凭据验证；
- `TaskCommandCoordinator`：暂停、继续、取消、重试和批量命令；
- `TaskContentCoordinator`：预览解析、文档读取、分享、打开文件夹和文件操作；
- `AppSettingsCoordinator`：设置修改、日志操作和应用更新入口。

已有 `MediaPreviewCoordinator`、`TaskDeletionCoordinator`、`TaskFileOperationCoordinator` 等组件继续复用，不创建重复抽象。

迁移顺序按照职责块执行。每迁移一块，`MainViewModel` 中对应方法仅保留薄委托；所有页面迁移稳定后，才考虑进一步缩小门面状态。

### 7.3 阶段三：拆解 `DownloadExecutor`

`DownloadExecutor` 保留任务级编排职责，并将具体工作委托给：

- `MediaTransferClient`：候选 CDN、请求、重试、字节写入和速度上报；
- `ImageDownloadExecutor`：单图、多图、动图和实况图；
- `VideoDownloadExecutor`：视频、独立音轨、合成与 MP4-only；
- `DocumentDownloadExecutor`：Markdown、文档资源和评论附件；
- `AttachmentDownloadExecutor`：通用附件下载；
- `OutputPublisher`：输出登记、临时文件提交和事务式重新下载。

平台解析器只提供标准化媒体描述和请求参数，不直接承担文件写入。底层传输组件不理解作者归档、页面导航或 Compose 状态。

第一步优先提取当前通用 `download()` 传输函数，因为它同时服务多种媒体，边界最明确；其余执行器随后逐类迁移。

### 7.4 阶段四：整理平台适配层

保留统一 `PlatformParser` 契约和路由，把仍位于公共文件中的具体平台入口移动回各自 `platform/<name>` 包。

每个平台包负责：

- 分享链接和内容 ID 的解析；
- 请求策略与平台特定请求头；
- 原始响应标准化；
- 作者资料与公开作品数据源；
- 平台特定登录检测和页面快照解析。

公共平台层只保留：

- 解析器契约；
- 路由；
- 通用错误类型；
- 登录状态模型；
- 品牌展示数据；
- 与平台无关的网络帮助函数。

本阶段暂不强制使用 Hilt multibinding。先让代码所有权清晰；如果手工路由成为新增平台的主要阻碍，再独立评估注册化。

### 7.5 阶段五：状态边界清理

完成前四阶段后进行定向清理：

- 删除已经失去调用者的兼容方法；
- 合并重复的任务状态判断；
- 把纯映射和策略提取为可单元测试函数；
- 清理跨 feature 的反向依赖；
- 补充关键类和公共接口注释；
- 更新架构文档和源码目录说明。

只有在所有调用已经迁移且测试证明等价时，才能删除兼容层。

## 8. 错误处理与并发安全

- 所有协程取消必须继续抛出 `CancellationException`；
- Worker 的成功、失败、重试和取消语义不得因类移动而变化；
- Room 写入和文件提交的先后顺序保持不变；
- 重新下载事务仍遵循新文件验证成功后再删除旧文件；
- 多任务速度采样、批次峰值和风控冷却继续由现有运行时控制器管理；
- ViewModel 或页面销毁不能中断已经交给 WorkManager 的下载；
- 新提取组件不得保存 Activity、Composable 或短生命周期 Context；
- UI 收集流时继续使用生命周期感知方式，避免重复订阅。

## 9. 测试策略

当前已有大量单元测试，重构采用表征测试优先：

1. 移动代码前为缺少覆盖的现有行为补测试；
2. 先验证旧实现测试通过；
3. 一次只移动一个职责块；
4. 运行相关定向测试；
5. 每阶段运行完整 `testDebugUnitTest` 和 Debug 构建；
6. 阶段完成后生成使用正式证书签名、但不启用 R8 的测试包；
7. 正式发布前再运行 R8 Release 构建和签名核对。

重点回归范围：

- 六个平台的单作品解析和下载；
- 支持平台的作者主页、分页和批处理；
- 风控暂停、手动尝试和自动恢复；
- B站多 P、音视频并行和合成；
- 图片、视频、音频、Markdown 与评论预览；
- 文件缺失、重新下载、删除和作者目录迁移；
- 登录 WebView 键盘、滚动、状态检测和 Cookie 复用；
- 应用切后台后的 Worker 与播放器行为；
- 旧数据库升级和旧任务读取。

## 10. 提交、验证与回滚

- 每个阶段至少一个独立提交；较大阶段按职责块拆成多个提交；
- 提交只包含本轮相关文件，不吸收工作区中无关删除或未跟踪文件；
- 每次提交使用项目所有者配置的 Git 作者身份；
- 默认不推送 GitHub，待本地试用确认后再汇总发布；
- 某阶段出现回归时优先回滚该阶段，不在未稳定基础上继续叠加；
- 不通过直接覆盖数据库、删除用户文件或清空设置来解决迁移问题。

## 11. 完成标准

满足以下条件才视为本轮架构重构完成：

- 用户可见功能、页面结果、下载文件和恢复行为与重构前一致；
- `MainViewModel` 不再直接实现解析、登录、任务、文件和更新的全部细节；
- `DownloadExecutor` 主要负责路由和编排，底层 HTTP 传输与各媒体处理具有独立边界；
- 首页、任务页和作者页的主要组件可分别定位和测试；
- 平台具体实现不再集中在公共平台文件中；
- `core` 不新增对 `feature` 或具体平台的依赖；
- 完整单元测试、Debug 构建和非 R8 签名测试包通过；
- 正式发布时 R8 构建、签名指纹和覆盖升级验证通过；
- README 和架构说明与最终目录一致。

行数只作为结果指标：目标是让主要超大文件降到约 500～800 行范围；如果某文件职责单一且继续拆分会增加跳转成本，可以保留更大体量，但必须在架构说明中解释。
